# ADR-015: TLS Certificate Management for Local Kubernetes GitOps Platform

## Status

Accepted

---

## Context

The PetClinic platform is deployed on a local Kubernetes cluster created with kind and managed using a GitOps workflow with ArgoCD.

Multiple platform components are exposed through Kubernetes Ingress resources, including:

- ArgoCD
- PetClinic
- Grafana
- Prometheus

Initially, these services were accessible only over HTTP. Although acceptable for basic local development, unencrypted communication does not reflect production environments and exposes management interfaces without transport encryption.

Because the platform uses local `.local` domain names, publicly trusted Certificate Authorities such as Let's Encrypt cannot issue certificates for these endpoints.

A certificate management solution is therefore required that satisfies the following requirements:

- provide HTTPS for all externally exposed platform services
- automatically issue and renew TLS certificates
- integrate with Kubernetes-native resources
- remain compatible with the GitOps deployment model
- support local development without external infrastructure
- centralize certificate management for all applications
- allow future migration to production Certificate Authorities with minimal configuration changes

---

## Decision

TLS certificate management is implemented using cert-manager together with a locally trusted Certificate Authority generated using `mkcert`.

The certificate architecture consists of:

- cert-manager deployed using ArgoCD
- local Certificate Authority generated by `mkcert`
- Kubernetes TLS Secret containing the local CA private key and certificate
- ClusterIssuer using the local CA
- individual Certificate resources for each application
- TLS-enabled Kubernetes Ingress resources
- automatic HTTP to HTTPS redirection

---

### 1. Local Certificate Authority

A local Certificate Authority is created using `mkcert`.

The CA certificate and private key are stored as a Kubernetes TLS Secret:

```text
local-ca-keypair
```

within the `cert-manager` namespace.

The secret is created during platform bootstrap and is intentionally managed outside GitOps because it contains the private key of the local Certificate Authority.

---

### 2. cert-manager deployment

cert-manager is deployed as an ArgoCD Application using the official Helm chart.

The deployment includes:

- cert-manager controller
- webhook
- CA injector
- Custom Resource Definitions (CRDs)

The platform bootstrap process waits until all cert-manager components and CRDs become fully available before creating certificate resources.

---

### 3. ClusterIssuer

A single ClusterIssuer is configured to use the local Certificate Authority.

All platform certificates are issued through this ClusterIssuer, providing centralized certificate management for the entire platform.

Using a ClusterIssuer avoids duplicating issuer configuration across namespaces while allowing certificates to be requested from any application namespace.

---

### 4. Application certificates

Each externally exposed application receives its own Certificate resource.

Dedicated TLS certificates are created for:

- ArgoCD
- PetClinic
- Grafana
- Prometheus

Each Certificate resource creates a Kubernetes TLS Secret that is consumed by the corresponding Ingress resource.

---

### 5. Secure Ingress configuration

All public Ingress resources are configured to:

- terminate TLS using cert-manager generated certificates
- redirect HTTP traffic to HTTPS
- expose services using encrypted connections

Each Ingress references its dedicated TLS Secret created automatically by cert-manager.

---

## Rationale

- cert-manager is the standard Kubernetes solution for certificate lifecycle management.
- `mkcert` provides locally trusted certificates without requiring public Certificate Authorities.
- A single ClusterIssuer simplifies certificate management across multiple namespaces.
- Individual certificates isolate application configuration and simplify future maintenance.
- TLS configuration remains fully declarative and compatible with GitOps.
- The architecture closely resembles production deployments while remaining suitable for local development.
- Replacing the local Certificate Authority with a production issuer requires only ClusterIssuer configuration changes while existing Certificate resources remain unchanged.

---

## Consequences

### Positive

- All platform services are available over HTTPS.
- Certificate issuance is fully automated.
- Certificate renewal is managed by cert-manager.
- TLS configuration is centralized and declarative.
- Applications remain independent of certificate management details.
- GitOps manages both applications and certificate resources.
- The solution closely matches production Kubernetes practices.
- Migration to a production Certificate Authority is straightforward.

### Negative

- Platform bootstrap becomes more complex.
- The local Certificate Authority must be trusted by developer machines.
- The local CA private key must be provisioned separately from GitOps.
- cert-manager becomes an additional platform dependency.
- Certificates issued by the local CA are trusted only on machines where the CA has been installed.

---

## Alternatives Considered

### 1. Self-signed certificates for each application

Rejected because each application would require manual certificate generation and trust management, making maintenance difficult.

---

### 2. Manual certificate generation using OpenSSL

Rejected because manual certificate lifecycle management is error-prone and difficult to automate within GitOps workflows.

---

### 3. Let's Encrypt

Rejected because the platform uses local `.local` domains that cannot be validated by public Certificate Authorities.

---

### 4. HTTP only

Rejected because it does not provide encrypted communication and differs significantly from production environments.

---

## Future Improvements

- Automate local CA provisioning during initial platform setup.
- Replace the local Certificate Authority with a production-compatible issuer for cloud deployments.
- Implement certificate expiration monitoring and alerting.
- Integrate certificate status metrics with Prometheus and Grafana.
- Support DNS-01 or ACME-based certificate issuance for production environments.
- Introduce certificate policy validation using Kubernetes admission policies.
- Automate verification that all public Ingress resources are protected by valid TLS certificates.
